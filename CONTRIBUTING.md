# Contributing

Thanks for looking. Being straight with you about what this is:

**These are personal projects with one maintainer.** They're public because the work is worth
showing and because bugs found by strangers are the most valuable kind — not because there's a
contributor pipeline waiting for you.

## What's genuinely welcome

- **Bug reports with a reproduction.** The single most useful thing you can send.
- **A case where the software claims something and doesn't do it.** These projects make specific,
  falsifiable claims. If one is false, that's the highest-value report there is.
- **Small, focused fixes** — a broken edge case, a wrong error message, a doc that lies.

## What will probably be declined

- **Large refactors or architecture changes.** Not because they're wrong; because reviewing them
  costs more than writing them, and the design is deliberate.
- **New features without a prior discussion.** Open an issue first. A PR that took you a weekend
  and gets declined is a bad outcome for both of us — the issue costs you ten minutes.
- **Style-only changes.** Formatting is settled.

## Before you open a pull request

1. **Open an issue first** for anything beyond an obvious fix.
2. **Make the test fail before you make it pass.** Every repository here holds to that; a test
   that has never been observed failing isn't evidence.
3. **Keep the diff scoped to one thing.** Unrelated changes bundled together get reviewed slowly
   or not at all.
4. **Say what you verified and how.** "It works" isn't a claim anyone can check.

## Response time

Best effort, from one person, around a day job. If something has gone quiet for two weeks, a
nudge on the thread is welcome and not rude.
